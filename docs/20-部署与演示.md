## 1. nginx 在系统里的职责

nginx 不出现在 `docker-compose.yml` 的服务名里，而是**内嵌在 `web` 服务镜像里**（`web/Dockerfile` 两阶段：node 构建 → nginx 托管），配置文件 `web/nginx.conf`。它只做四件事：

1. **静态托管 + 前端路由回退**：托管 Vite 构建产物 `dist/`，`vue-router` history 模式遇到非真实文件一律回退 `index.html`（`try_files $uri $uri/ /index.html`）。
2. **gzip 压缩**：大屏依赖 ECharts / Element Plus，体积大，gzip 降带宽（>1KB 的 text/css/js/json/svg 等）。
3. **静态资源长缓存**：Vite 产物带内容 hash，`*.js/css/png/...` 缓存 7 天（`expires 7d`），`index.html` 不走此规则保证发版即时生效。
4. **同源反向代理到 center**（核心职责）：
   - `location /api/` → `proxy_pass http://center:5100`：REST API，透传 `/api/...` 前缀，带 `Host` / `X-Real-IP` / `X-Forwarded-*`。
   - `location /hubs/` → `proxy_pass http://center:5100`：SignalR 实时推送，**必须带 `Upgrade` / `Connection: upgrade` 头**，读/写超时放宽到 3600s（WebSocket 长连接）。

**为什么需要 nginx（设计意图）**：后端 CORS 只放行 dev 源 `http://localhost:5173`（`Program.cs`），生产浏览器直连 center 必然跨域被拦；由 nginx 做同源反代，浏览器只认 `:8088` 一个源，天然规避 CORS，同时把静态资源、REST、WebSocket 收敛到同一入口。**对外只暴露 `8088`，center 不出现在公网。**

## 3. 上线前必改清单（按优先级）

> 以下为 2026-08-27 盘点核实的问题，**未修复前不要直接上线**。

### 3.1 端口不一致（阻塞，必改）
- 事实：`src/NitroCloud.Api/appsettings.json` `Urls = http://0.0.0.0:5110`，但 `web/nginx.conf`、`web/vite.config.ts`、README、Dockerfile 注释全部指向 **5100**（commit `27a3a16` 改 appsettings 时未同步反代）。
- 后果：`web` 容器 `/api`、`/hubs` 反代到 `center:5100` 而服务实际监听 `5110` → **502**；本地 dev 的 Vite 代理同样失效。
- 修法（二选一，推荐前者）：`appsettings.json` 改回 `5100`，或把 nginx/vite/README 统一到 `5110`。改完用 `docker compose up -d --build` + 浏览器验证大屏。

### 3.2 center 未暴露健康检查与指标（运维缺口）
- 事实：`docker-compose.yml` 中 center **无 `ports`、无 `healthcheck`**；InfluxDB 也未映射宿主端口；README 声称的 `http://IP:5100/healthz`、`/metrics`、`http://IP:8086` 当前均不可达。
- 修法：center 增加 `ports: ["5100:5100"]`（或 nginx 反代 `/healthz`、`/metrics`），compose 补 center `healthcheck`（`curl -fsS http://localhost:5100/healthz`）并让 web `depends_on` 条件改为 `service_healthy`；需要时给 influx 映射 `8086`。

### 3.3 默认口令 / Token（安全，必改）
- `.env.example` 默认 `admin123456` / `dev-token`：EMQX dashboard、InfluxDB admin/UI 全默认口令。
- **InfluxDB 凭据首次启动即固化**，改动需 `docker compose down -v` 重建卷（会丢时序数据，上线前定好）。
- 上线流程：首次部署前编辑 `.env` 换强口令 → 再拉起；勿把 `.env` 提交。

### 3.4 尚缺项（排期做）
- DoD 5 Command 模块 + `CommandsController`（前端已就绪）。
- 修复 6 项既有测试失败。
- CI/CD：`.github/workflows/` 落地（build + test + 镜像构建）。
- 生产级入口：TLS（HTTPS）、登录鉴权、限流、防火墙只暴露必要端口。

## 4. 运维手册（上线后）

### 4.1 日常命令
```bash
docker compose up -d --build   # 全链路拉起（修好 §3.1 后）
docker compose up -d           # 仅 broker + influx（本地联调）
docker compose down            # 停服务（保留数据卷）
docker compose down -v         # 停 + 删数据卷（慎用，会丢 Influx/SQLite 数据）
docker compose logs -f center  # 看 center 日志
```

### 4.2 健康与监控
- `GET /healthz`：SQLite 连通性检查（tag `db/ready`）；`GET /metrics`：Prometheus 格式指标（含 `cloud_mqtt_connect_failure_total` 等）。**前提是先把 §3.2 暴露出去**。
- 建议接 Prometheus + Grafana 抓 `/metrics`，配置告警：MQTT 断连计数、center 进程存活、`/healthz` 失败。

### 4.3 数据与备份
- **SQLite（center-data 卷，`/data/nitrocloud.db`）**：元数据 + 告警。源码目录 `backups/` 已有手工 `.bak` 惯例；生产定期 `sqlite3 /data/nitrocloud.db ".backup '...'"` 或卷快照，并做恢复演练。库结构变更走 FluentMigrator 迁移，不手动改库。
- **InfluxDB（influx-data 卷）**：时序数据只进这里，bucket `nitrocloud`、measurement `device_point`、保留 30 天。用 `influx backup` / `influx restore` 或卷快照；监控磁盘增长，数据量大时规划下采样/长期归档。
- 日志：center Serilog 文件日志（`logs/`，按天滚动保留 14 天）+ stdout；生产把日志卷挂出或接日志采集。

### 4.4 中间件维护
- **EMQX**：控制台 `:18083`，管理客户端/ACL（生产给网关注册独立用户名口令）；broker 可拆多机集群（本期单机）。
- **镜像版本已固定**（`emqx:5.8.3` / `influxdb:2.7` / `node:22-alpine` / `nginx:stable-alpine` / `dotnet sdk:10.0`）：升级依赖包需用户明确要求（AGENTS.md 雷区）。

### 4.5 契约与升级纪律
- 上行/下行契约以 NitroGateway 侧为准；命令契约需网关补订阅处理器，属可接受小改动。
- 发版回滚：镜像打 tag、保留上一版本镜像；`down` 旧容器 `up` 新容器。
